# KagiLink core FFI boundary design (proposed, not implemented)

Status: PROPOSED (D016). Nothing here is implemented or reviewed. The Windows (lead) session
owns it. Other platform sessions must not start FFI bindings, CPace ports or vector ports until
the owner approves this design and the Windows session says so.

Goal: let Windows (C++), iOS/macOS (Swift) and Android (Kotlin/JNI) use the single Rust core
(`core/kagilink-core`, D014) without re-implementing the handshake, and without widening the
attack surface or leaking secrets across the boundary.

## Principles

1. `kagilink-core` keeps `#![forbid(unsafe_code)]`. All `unsafe` lives in one new crate,
   `core/kagilink-ffi` (crate types `staticlib` + `cdylib`), kept as small as possible.
2. Plain C ABI, hand-reviewed header generated by cbindgen and committed. No UniFFI or other
   generated glue in v1: fewer moving parts, an auditable surface, same shape on all targets.
3. Hardware, approval UI, BLE and target input stay on the platform side. The core never
   touches Keychain, Keystore, StrongBox, TPM, Secure Enclave or the UI.
4. Fail closed: any error, panic, null pointer or bad length returns a status code and leaves
   no usable secret state behind.

## Handle model

Opaque pointers, created and freed only through the library:

| Handle | Wraps | Created by | Ends when |
|---|---|---|---|
| `kl_receiver_t*` | `ReceiverSession` | `kl_receiver_new` | `kl_receiver_free` |
| `kl_sender_t*` | `SenderPending` | `kl_sender_start` | consumed by `kl_sender_finish`, or `kl_sender_free` |
| `kl_channel_t*` | `SecureChannel` | `kl_receiver_finish` / `kl_sender_finish` | `kl_channel_free` |

- `*_free` zeroizes (the Rust types already erase on drop), is idempotent for NULL, and a
  freed handle must not be reused. `kl_sender_finish` consumes the sender handle even on
  failure, mirroring `handle_m3(self, ..)`.
- Handles are not thread-safe. Each handle is used from one thread at a time; the library
  guards with a mutex and returns `KL_ERR_BUSY` on concurrent entry instead of blocking.

## Data across the boundary

- Messages (M1..M4, fragments, plaintext) use caller-allocated buffers:
  `status fn(handle, const uint8_t* in, size_t in_len, uint8_t* out, size_t* out_len)`.
  `*out_len` is capacity on entry and written length on exit; too small returns
  `KL_ERR_BUFFER` with the required size, without consuming protocol state.
- The library returns no Rust-allocated memory except opaque handles. No callbacks into the
  host, no global mutable state, no logging.
- The six-digit code is written only by `kl_receiver_code` into a caller buffer for display
  while active. Received plaintext is written into a caller buffer; the caller must wipe it
  (`kl_secure_wipe` is provided) as soon as it has been used. This is documented as the
  host's duty; the library cannot guarantee host-side copies are erased.
- Randomness and time come from the OS CSPRNG and a monotonic clock inside the library.
  Injected RNG/clock exist only behind a `test-hooks` Cargo feature that release builds
  must not enable (checked in CI).

## Errors

- `kl_status_t` is a stable integer mapped one-to-one from `Error` (Expired, NotActive,
  TooManyFailures, Malformed, Unsupported, WrongState, Pake, ConfirmationFailed, BadCode,
  Authentication, Framing, Limits, CounterExhausted, NotApproved, Closed, Randomness), plus
  `KL_ERR_NULL`, `KL_ERR_BUFFER`, `KL_ERR_BUSY`, `KL_ERR_PANIC`, `KL_ERR_ABI`.
- No error text, no secret, no offset-into-secret information crosses the boundary. The
  host must not distinguish "wrong code" from "bad confirmation" to the user beyond what the
  policy allows.
- Every exported function wraps its body in `catch_unwind`; the FFI crate builds with
  `panic = "abort"` in release so a panic can never unwind into foreign frames, and the
  catch path is only a defence for debug builds.

## Policy hooks that must stay on the host side

- Approval: `kl_channel_approve_one_transfer` is called only after the platform's own user
  approval (biometric/device credential where required). The core consumes the permission
  per transfer (`seal` of a SECRET message).
- Readiness: `kl_channel_set_ready_to_receive(true)` only while a verified safe input target
  exists (Phase 5 evidence; RDP stays blocked until demonstrated).
- Limits: only the receiver enforces TTL/three-failure (D014); the sender side exposes no
  way to extend them.
- Hardware gates (StrongBox, Secure Enclave/Keychain, TPM) run before the host may call the
  secret-sending functions; failure means the host never calls them.

## ABI versioning and compatibility

- `kl_abi_version()` returns a single integer; each binding checks it at start and refuses on
  mismatch (`KL_ERR_ABI`). The wire protocol version/suite is separate (PROTOCOL.md v1,
  exact match, no negotiation).
- Any signature or struct change bumps the ABI version. Structs are avoided; the surface is
  functions plus opaque handles and byte buffers.

## Per-platform binding sketch

- Windows: link the `staticlib` into the C++20 receiver; header consumed directly. Target
  `x86_64-pc-windows-msvc` (and `aarch64` later).
- iOS/iPadOS/macOS: `staticlib` per target (`aarch64-apple-ios`, `-ios-sim`, `-darwin`)
  packaged as an XCFramework; Swift calls the C header through a module map.
- Android: `cdylib` per ABI (`aarch64-linux-android` first, StrongBox devices only); a thin
  JNI shim passes `ByteArray` buffers, with no key material ever stored in the JVM heap by
  the shim beyond the call.

## Open items and risks

- Not yet verified: that `pakery-*`, `getrandom` 0.4 and the other pinned crates build and
  pass the test suite on every target above (iOS, Android, aarch64). This must be tested
  before any platform commits to the design.
- Memory hygiene: Rust-side erasure is best effort (D014 notes stack copies are untracked).
  Host buffers, JNI arrays and Swift `Data` copies are outside the library's control.
- Reproducible builds, symbol visibility (export only `kl_*`), CFI/hardening flags and a
  Cargo feature check in CI are not designed yet.
- Whether a C ABI is preferable to UniFFI is a recommendation, not a measured result.
- Independent review of `unsafe` in the FFI crate is required before any real-secret use.

## Not in scope

BLE mapping (Phase 2), hardware-backed approval details (Phase 3), the encrypted vault, and
any change to the v1 wire protocol or security policy.
