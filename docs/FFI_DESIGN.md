# KagiLink core FFI boundary design (conditionally approved, not implemented)

Status (update 2026-11-05, D021: preconditions met, binding spike open): CONDITIONALLY APPROVED by the owner on 2026-11-05 (D016: plain C ABI, Windows session implements, four preconditions listed in DECISIONS.md D016). Originally PROPOSED. Nothing here is implemented or reviewed. The Windows (lead) session
owns it. Other platform sessions must not start FFI bindings, CPace ports or vector ports until
the D016 preconditions are met and the Windows session says so.

Goal: let Windows (C++), iOS/macOS (Swift) and Android (Kotlin/JNI) use the single Rust core
(`core/kagilink-core`, D014) without re-implementing the handshake, and without widening the
attack surface or leaking secrets across the boundary.

## Principles

1. `kagilink-core` keeps `#![forbid(unsafe_code)]`. All `unsafe` lives in one new crate,
   `core/kagilink-ffi` (crate types `staticlib` + `cdylib`), kept as small as possible.
2. Plain C ABI, hand-reviewed header generated by cbindgen and committed. No UniFFI or other
   generated glue in v1: fewer moving parts, an auditable surface, same shape on all targets.
3. Hardware, approval UI, BLE and target input stay on the platform side. The core never
   touches Keychain, Keystore, StrongBox, TPM, Secure Enclave or the UI.
4. Fail closed: any error, panic, null pointer or bad length returns a status code and leaves
   no usable secret state behind.

## Handle model

Opaque pointers, created and freed only through the library:

| Handle | Wraps | Created by | Ends when |
|---|---|---|---|
| `kl_receiver_t*` | `ReceiverSession` | `kl_receiver_new` | `kl_receiver_free` |
| `kl_sender_t*` | `SenderPending` | `kl_sender_start` | consumed by `kl_sender_finish`, or `kl_sender_free` |
| `kl_channel_t*` | `SecureChannel` | `kl_receiver_finish` / `kl_sender_finish` | `kl_channel_free` |

| `kl_reassembler_t*` | `ble_frame::Reassembler` + one held message | `kl_reassembler_new` | `kl_reassembler_free` |

- `*_free` zeroizes (the Rust types already erase on drop), is idempotent for NULL, and a
  freed handle must not be reused. `kl_sender_finish` consumes the sender handle even on
  failure, mirroring `handle_m3(self, ..)`.
- Handles are not thread-safe. Each handle is used from one thread at a time; the library
  guards with a mutex and returns `KL_ERR_BUSY` on concurrent entry instead of blocking.
- Handles are registry tokens, not pointers (see "Handle registry" below). Stale, doubled,
  forged, NULL and wrong-type handles return `KL_ERR_NULL` (frees are no-ops); a free racing a
  call is memory-safe. No ABI change: the exported signatures and `KL_ABI_VERSION` (2) are
  unchanged because the pointer-typed handle is still pointer-sized and opaque to C.
- Input and output buffers of one call must not overlap (documented, not checked).

## Handle registry (implemented, replaces the raw `Box` pointers)

Resolves the independent-review finding that a free racing a call, a stale handle or a double
free was use-after-free (the old `try_lock` only guarded concurrent non-free calls).

- Layout: a global `Mutex<Registry>` holds a slab of slots `{generation, Option<Arc<dyn Any>>}`
  plus a free list. A handle value is `((generation << IDX_BITS) | slot) ^ mask` cast to the C
  pointer type; it is never dereferenced. 64-bit: 24 index bits, 40 generation bits; 32-bit: 12 and
  20. `mask` is a per-process value from `std` `RandomState` generated on first use: it only makes
  accidental hits by arbitrary integers or addresses negligible and is NOT a secret or a security
  boundary. Generation 0 and the value 0 are never issued, so NULL and small integers always fail.
- Every call: `resolve` locks the registry, validates slot + generation + type, clones the `Arc`,
  and releases the registry lock before touching the object. A concurrent free therefore cannot
  free memory under a live call; the memory lives until the last clone drops.
- Free: `unregister` removes the slot and bumps its generation under the registry lock (the
  token is dead from that instant, for every copy), then OUTSIDE the lock the object is wiped
  under its own mutex and the last `Arc` drops. Secrets are explicitly erased (receiver session and
  sender pending state dropped, channel closed and held plaintext dropped, reassembler held data
  zeroized) before `*_free` returns, even when another call holds a clone: the free waits for that
  in-flight call (a blocking lock, short because no export blocks or calls back) and then wipes,
  recovering a poisoned mutex. A late call that already held a clone then sees an erased object
  (`KL_ERR_NULL` or `KL_ERR_CLOSED`). Dropping the last `Arc` zeroizes through the core types as
  before.
- Double free, stale free, wrong-type free and garbage free are no-ops (nothing changed). Two
  racing frees of one token: exactly one wins; the loser returns immediately and may return before
  the winner finished erasing.
- Lock order: the registry lock is a leaf, held only for a table lookup, insert or remove. It is
  never held while an object mutex is taken, while core code runs or while an `Arc` is dropped;
  an object mutex is never held while the registry lock is taken (finish functions release the
  object guard before registering the new channel). No deadlock is possible between them. A thread
  panicking inside an export is caught; a poisoned registry mutex is recovered.
- `try_lock`/`KL_ERR_BUSY` semantics for concurrent non-free calls are unchanged.
- Status codes: no new value; a dead handle reuses `KL_ERR_NULL`. `kl_channel_is_closed` and
  `kl_reassembler_is_dead` return 1 for them. Registry full returns `KL_ERR_LIMITS`.
- Remaining limits: generation wrap after 2^40 (64-bit) or 2^20 (32-bit) reuses of one slot could
  alias a very old token; at most 2^24-1 (2^12-1 on 32-bit) live handles; the output-slot pointer
  (`kl_*_t**`) and the data buffers are still caller-supplied raw pointers and are trusted
  (non-NULL, writable, non-overlapping) exactly as before; a host that frees while it still
  has a call outstanding gets defined behaviour but a failed call; the registry is process-global
  state shared by every library user in the process. Unsafe code was not run under Miri or a
  sanitizer.

## Data across the boundary

- Messages (M1..M4, fragments, plaintext) use caller-allocated buffers:
  `status fn(handle, const uint8_t* in, size_t in_len, uint8_t* out, size_t* out_len)`.
  `*out_len` is capacity on entry and written length on exit; too small returns
  `KL_ERR_BUFFER` with the required size, without consuming protocol state.
- The library returns no Rust-allocated memory except opaque handles. No callbacks into the
  host, no global mutable state, no logging.
- The six-digit code is written only by `kl_receiver_code` into a caller buffer for display
  while active. Received plaintext is written into a caller buffer; the caller must wipe it
  (`kl_secure_wipe` is provided) as soon as it has been used. This is documented as the
  host's duty; the library cannot guarantee host-side copies are erased.
- Randomness and time come from the OS CSPRNG and a monotonic clock inside the library.
  Injected RNG/clock exist only behind a `test-hooks` Cargo feature that release builds
  must not enable (checked in CI).

## Errors

- `kl_status_t` is a stable integer mapped one-to-one from `Error` (Expired, NotActive,
  TooManyFailures, Malformed, Unsupported, WrongState, Pake, ConfirmationFailed, BadCode,
  Authentication, Framing, Limits, CounterExhausted, NotApproved, Closed, Randomness), plus
  `KL_ERR_NULL`, `KL_ERR_BUFFER`, `KL_ERR_BUSY`, `KL_ERR_PANIC`, `KL_ERR_ABI`.
- No error text, no secret, no offset-into-secret information crosses the boundary. The
  host must not distinguish "wrong code" from "bad confirmation" to the user beyond what the
  policy allows.
- Every exported function wraps its body in `catch_unwind`; the FFI crate builds with
  `panic = "abort"` in release so a panic can never unwind into foreign frames, and the
  catch path is only a defence for debug builds.

## Policy hooks that must stay on the host side

- Approval: `kl_channel_approve_one_transfer` is called only after the platform's own user
  approval (biometric/device credential where required). The core consumes the permission
  per transfer (`seal` of a SECRET message).
- Readiness: `kl_channel_set_ready_to_receive(true)` only while a verified safe input target
  exists (Phase 5 evidence; RDP stays blocked until demonstrated).
- Limits: only the receiver enforces TTL/three-failure (D014); the sender side exposes no
  way to extend them.
- Hardware gates (StrongBox, Secure Enclave/Keychain, TPM) run before the host may call the
  secret-sending functions; failure means the host never calls them.

## ABI versioning and compatibility

- `kl_abi_version()` returns a single integer; each binding checks it at start and refuses on
  mismatch (`KL_ERR_ABI`). The wire protocol version/suite is separate (PROTOCOL.md v1,
  exact match, no negotiation).
- Any signature or struct change bumps the ABI version. Structs are avoided; the surface is
  functions plus opaque handles and byte buffers.
- History: v1 = handshake and secure channel (18 exports); v2 (D027, 2026-11-06) adds
  the BLE chunk codec. Adding functions also bumps the version so a v1 host refuses a v2 library
  and the reverse. v3 (D030, 2026-11-06) adds the read-only `kl_receiver_failures` (below), again
  bumping the version by the same rule. Places that record the number: `KL_ABI_VERSION` in `lib.rs`
  and `kagilink.h`, `EXPECTED_ABI` in `apps/android/ffi-spike/binding/Native.kt`, the
  `abi_version_is_three` test; the C, C++ and Swift consumers compare against the header constant.

## BLE chunk codec (ABI v2, D027)

Exposes `kagilink-core::ble_frame` (docs/BLE_GATT_SPEC.md section 5) so no platform re-implements
it. The codec is pure and carries opaque bytes; it adds no cryptography and trusts nothing the radio
delivers.

| Function | Purpose |
|---|---|
| `kl_frame_chunk(mtype, msg, len, max_chunk, out, out_len, out_count)` | split one message into chunks (6..=512 bytes each); `out` = repeated `[u32 BE length][chunk]`, `out_count` = chunks; stateless, BUFFER reports the required size |
| `kl_reassembler_new/free` | opaque strict in-order reassembler for one direction of one connection |
| `kl_reassembler_push(h, chunk, len, out_complete)` | OK with `*out_complete` 0 = need more, 1 = message complete and held; error = reassembler dead for good (later pushes return `KL_ERR_CLOSED`) |
| `kl_reassembler_take(h, out_mtype, out, out_len)` | copy the held message (type and data) out; BUFFER keeps it held, success erases the held copy; nothing held = `KL_ERR_WRONG_STATE` |
| `kl_reassembler_is_dead(h)` | 1 once a codec error happened (also for NULL/busy) |
| `kl_ack_chunk(seq, out, out_len)` / `kl_parse_ack(chunk, len, out_is_ack, out_seq)` | D026 Notify ACKs; "not an ACK" is `KL_OK` with `*out_is_ack` = 0, so hosts filter ACKs before the reassembler (which rejects them) |

Design choices: one length-prefixed buffer instead of an index getter (the same shape as
`kl_channel_seal`, one call, no per-index state); a completed message stays inside the handle until
taken so a too-small buffer never loses it; `push` while a message is held returns
`KL_ERR_WRONG_STATE` and changes nothing; an error from `in_slice` or a NULL argument (before the codec
sees the chunk) does not kill the reassembler, but hosts should treat every non-OK push as "drop the
connection". Error mapping is the core one: Malformed (reserved/ACK bits, short or over-512 chunk),
Framing (duplicate, gap, reorder, bad first chunk, LAST/length mismatch), Limits (declared length 0 or
above 512), Unsupported (unknown message type), Closed (after an error). Test evidence is listed in
IMPLEMENTATION_STATUS.md; real BLE use of this API is not tested.

## Receiver failure budget getter (ABI v3, D030)

`kl_receiver_failures(r, out_used, out_max)` returns the receiver's use of the three-failure budget so
hosts display the core's number instead of deriving it (the macOS spike did and could drift).

- `*out_used` = core `ReceiverSession::failures_including_open()`: attempts that already sent M3 and
  have not succeeded, counting an open one (D026); the same definition as the Windows receiver.
  `*out_max` = `MAX_FAILURES` (3).
- Read-only: it changes no session state and exposes no code or key material. It keeps working after
  expiry, success and budget exhaustion and then returns the final count with `KL_OK`.
- Errors: `KL_ERR_NULL` for a NULL, stale, forged, freed or wrong-type handle (registry lookup, as for
  every getter) and for NULL out pointers (outputs untouched); `KL_ERR_BUSY` if another call holds the
  handle. Panics are caught (`KL_ERR_PANIC`); nothing unwinds across the boundary.
- Tests: `receiver_failures_*` in `core/kagilink-ffi/tests/ffi.rs` (0/3, open attempt after M3,
  3/3 after the budget is spent, after success, NULL/stale/wrong-type/garbage handles, NULL out
  pointers) and a unit test with a manual clock for the expired case. C++ wrapper: `Receiver::failures`.

## Per-platform binding sketch

- Windows: superseded by D022: the Windows receiver is written in Rust and links the core crate directly, so there is no FFI boundary on Windows (the C and C++ consumers stay as tests of the C ABI for other hosts). Target
  `x86_64-pc-windows-msvc` (and `aarch64` later).
- iOS/iPadOS/macOS: `staticlib` per target (`aarch64-apple-ios`, `-ios-sim`, `-darwin`)
  packaged as an XCFramework; Swift calls the C header through a module map.
- Android: `cdylib` per ABI (`aarch64-linux-android` first, StrongBox devices only); a thin
  JNI shim passes `ByteArray` buffers, with no key material ever stored in the JVM heap by
  the shim beyond the call.

## Open items and risks

- Not yet verified: that `pakery-*`, `getrandom` 0.4 and the other pinned crates build and
  pass the test suite on every target above (iOS, Android, aarch64). This must be tested
  before any platform commits to the design.
- Memory hygiene: Rust-side erasure is best effort (D014 notes stack copies are untracked).
  Host buffers, JNI arrays and Swift `Data` copies are outside the library's control.
- Reproducible builds, symbol visibility (export only `kl_*`), CFI/hardening flags and a
  Cargo feature check in CI are not designed yet.
- Whether a C ABI is preferable to UniFFI is a recommendation, not a measured result.
- Independent review of `unsafe` in the FFI crate is required before any real-secret use.

## Not in scope

BLE mapping (Phase 2), hardware-backed approval details (Phase 3), the encrypted vault, and
any change to the v1 wire protocol or security policy.
