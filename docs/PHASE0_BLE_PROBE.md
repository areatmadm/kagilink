# KagiLink native BLE feasibility probes

These native targets are Phase 0 research, not Phase 4 products. No secret input,
vault, pairing code, PAKE, authenticated peer, production transfer or RDP exists.
Use one sender and one receiver at a time, with explicit local start actions.
Anyone nearby can spoof or interrupt this unauthenticated public diagnostic.

## Separate diagnostic contract

| Item | Fixed value |
|---|---|
| Service | `7d9a0001-6f8e-4d52-9b91-89c767b6e201` |
| Characteristic | `7d9a0002-6f8e-4d52-9b91-89c767b6e201` |
| Properties | Write with response, read; no notifications |
| Request | ASCII `KagiLink-P0-PING` (16 bytes) |
| Response | ASCII `KagiLink-P0-PONG` (16 bytes) |
| Lifetime | At most 60 monotonic seconds from explicit start |
| Receiver scan | 10 seconds; reject zero or multiple observed senders |

These identifiers are for diagnostics only and MUST NOT become the production
service or an alternate unencrypted production transport. PROTOCOL.md is unchanged.
16-byte values fit the default 20-byte ATT value budget; this does not test larger
MTUs, fragmentation, notifications, cryptography, replay resistance or authentication.
Static request/reply values can be replayed; a pass means only this fixed exchange
was observed. The receiver does not automatically choose another sender or retry.

Sender accepts exactly one complete offset-zero request, rejects prepared writes,
wrong bytes/lengths and repeats, and binds the read to the same transient central.
It answers one offset-zero read with the fixed response. No received bytes, routing
IDs, personal device names or error descriptions are displayed or saved. A reply
queued to the platform is not receiver delivery evidence. Only the receiver checks
exact response bytes and reports exchange success.

App background/inactive transition, stop, expiry or API error closes the attempt.
Apple's peripheral API does not report an ordinary central disconnect without
additional subscription behavior here; abandoned public state expires, and is not
a production disconnect-cleanup implementation. OS cancellation/disconnect timing
and ATT response delivery after stop need real-device tests. No key or secret state
is ever created by these probes. Hardware availability labels are explicitly
unverified; StrongBox/Enclave key operations remain a separate Phase 0 gate.

## Targets and first run

1. Windows: build `apps/windows/build-probe.ps1`. On a normal Medium-integrity
   desktop run `target/phase0/kagilink-phase0-probe.exe --ble-test`. Low/elevated
   processes refuse before scanning. GATT consent/packaging may block this console
   context; record the failure and do not elevate, pair automatically or bypass it.
2. Android: open `apps/android` in Android Studio with SDK platform 37.2, build tools
   37.0.0 and JDK 17+. Use Gradle 9.8.2 with AGP 9.5.0. The research app requires
   Android 14/API 34+
   and requests Nearby Devices advertising/connect permissions. Grant permission,
   tap start again, and keep the app in front. Start the receiver during the window.
3. iOS/iPadOS: open `apps/apple/KagiLinkPhase0.xcodeproj` with full Xcode. The
   `KagiLink-iOS-Phase0` target runs on iOS/iPadOS 18+ and builds with the explicit
   iOS SDK 27.1. The build helper refuses a missing/mismatched SDK. Build without
   signing using the script below. A physical-device install needs separately authorized existing
   signing/provisioning; this task does not create accounts or certificates.
4. macOS: the same project has `KagiLink-macOS-Phase0`, Apple Silicon/macOS 14+.
   Choose sender advertisement or receiver scan. The app sandbox requests Bluetooth
   only. Unsigned build success does not verify entitlements or runnable hardware.

On Mac, `sh apps/apple/build-probes.sh` compiles both Apple targets without signing,
installation, certificate creation or publication. There are no Swift packages.
`sh apps/apple/build-probes.sh --simulator` selects the exact simulator SDK 27.1
instead; simulator build/execution cannot establish hardware-backed security.
`sh apps/apple/test-build-script.sh` tests only mocked tool invocations and SDK
rejection behavior, without invoking Xcode or a simulator.
For Android, use a verified Gradle installation; the PowerShell build helper checks
the exact version and requires an existing SDK. On Mac the equivalent is:

```sh
sh apps/android/build-probe.sh /path/to/gradle-9.8.2/bin/gradle
```

No SDK download, SDK-license acceptance or device install is automated. Android
debug builds explicitly disable signing; no local certificate is created by the
configured build. Device installation requires separately authorized signing.
Dependency locks were generated by real SDK-independent Gradle resolution and are
saved as source candidates. This is not Android compilation: validate the locks
on the first SDK build, reviewing any needed lock update rather than silently
rewriting them during every build. Current results are in IMPLEMENTATION_STATUS.md.

## Mobile glass and adaptive layout

Both mobile interfaces use Liquid Glass styling without changing the diagnostic
security boundary. Apple uses the public native glass API on supported OS versions
([Apple's custom-view guidance](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views))
and system material on iOS 18; Android uses its own platform-rendered translucent
surfaces. Do not describe the Android appearance or iOS 18 fallback as Apple's
native Liquid Glass implementation. Text, unsupported states and stop controls must
remain readable with reduced transparency, large fonts and screen readers.

The Android SDK selection follows the stable packages in
[Google's SDK repository metadata](https://dl.google.com/android/repository/repository2-3.xml).
The iOS build requirement follows [Apple's iPhone Duo preparation guidance](https://developer.apple.com/iphone-duo/prepare/):
SDK 27.1 enables the new full-display layout and vertical system bars. Respect safe
areas and available space rather than assuming an iPhone model, fixed display size
or orientation. Verify outer/inner display transitions and resizing on Duo; source
and plist checks cannot establish that visual/device result.

## Required device evidence

Record a sanitized matrix: sender/receiver OS versions, radio/adapter model,
permission state, foreground state and terminal result; exclude device addresses,
account names and received bytes. Test Windows↔Android, Windows↔iOS/iPadOS,
Windows↔macOS, macOS↔Android and macOS↔iOS/iPadOS. Two macOS devices are needed
to exercise macOS↔macOS without changing the one-role-at-a-time UI.

Test denied permission, radio off, unsupported hardware, no sender, two senders,
background/foreground, early disconnect, expiry, cancel, malformed write, duplicate
write/read and wrong read order. A successful fixed exchange is only one part of
the Phase 0 exit criteria; production cryptography, hardware key use, input safety
and the full transport matrix still gate later phases.
